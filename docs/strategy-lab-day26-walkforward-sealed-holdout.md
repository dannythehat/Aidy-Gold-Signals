# Day26 — Chronological out-of-sample, purge/embargo and registered one-time holdout

**Build date:** 15 October 2026. AIDY's locked Day26 criterion is *“Walk-forward, chrono splits, purge/embargo, trial registration; PASS: leakage fixtures fail, holdout sealed from tuning.”* This build implements a strict operational research protocol on actual retrospective XAUUSD source data without falsely asserting strategy alpha or broker fill parity. It is independent of GoldThinker and does not alter live trading.

## Implemented software

- `src/aidy/strategy_lab_oos_protocol.py` constructs **causal closed M5 feature/target observations** using the Day07 real HistData reader. A decision feature is only available at its fully CLOSED bar. Its horizon-2 bid-price-change label is only mature after two subsequent fully closed M5 bars. Historical source digest, archive SHA, fixed-EST source clock qualification, exact sequential UTC bars, bid-only basis and archival retrospective/PIT labels must all pass.
- Strict **expanding walk-forward** folds: minimum 32 observations in training, validation batches of 12, source-order preserved, 2 closed bars embargo plus source label-maturity purge before every validation start. Training sample outcomes must have actually become available by the embargo cutoff. Multiple folds required and recorded as immutable UTC train/validation start/end summaries, counts, train-only model direction and sign correctness (not profits).
- An explicit sealed final holdout of 20 labelled M5 observations is kept OUT of the development accessor, with four excluded boundary observations (2 embargo + 2 labelled-horizon bars) between development and holdout. The toy prior-mean-sign classifier is fixed and its complete rule hash recorded; it fits exclusively on **development** label results and cannot tune on holdout labels in supported API flow.
- `src/aidy/strategy_lab_oos_trial_registry.py` is a separate **real on-disk SQLite append-only event store** with immutability triggers, SHA256 per-event chaining, frozen data/policy/rule/fold/holdout digests, uniquely reserved (source SHA, strategy family) to prevent restarting the same hypothesis under a different name in one registry. Supported state machine: `register -> freeze -> reveal`. Reveal BEFORE freeze, a second reveal, changed policy/source/folds, duplicate family, modified/tampered record and manual UPDATE/DELETE are refused.
- `scripts/strategy_lab/day26_sealed_oos_real_history.py` fetches genuine frozen-source XAUUSD HistData bid M1 using prior read-only BigQuery reader, derives 120 completed M5 bars from 600 M1 on 2025-01-06 11:00–21:00 UTC, computes development folds, runs real SQLite registry life cycle, performs a **single** holdout reveal, tests repeated reveal rejection, and replays a second independent source BigQuery read with same digest. JSON proof and two real query job IDs archived in GitHub CI.
- Tests `tests/test_strategy_lab_oos_protocol.py` and `tests/test_strategy_lab_day26_real_history.py` verify known/sample fold boundaries, label maturation, lookahead/future-bar rejection, insufficient history, change of policy, dangerous shorter embargo, altered data, all registry transitions/tampering, forbidden second final access and deterministic replay. Entire Day07/22 historical reader and earlier Day24/25 chain also regression tested.

## Methodological nuance and limitations

- **Forward-only with purge AND embargo:** the embargo is a *pre-validation gap*: earliest eligible training label must mature before `first_validation_decision - 2*5 minutes`. This approach protects overlapping labels in this small expanding chronology. It does **not** purport to implement every combinatorial purged cross-validation protocol, probabilistic multiple-testing adjustment or independent market regime protocol. Those are further research stages.
- **Holdout access protection is an audited engineering interface, not physical data secrecy.** An attacker/researcher with direct access to the entire raw warehouse (or module internals) could circumvent an in-process or single-process seal. Truly segregated role-based training vs test access, separately administered test-runner permissions and production proof of denial belong to deployment hardening. Our CI demonstrates the official API refuses access until freeze and then only once, and records event-chain proof.
- **Point-in-time honesty:** original historical feed is explicitly `retrospective_history` and `pit_eligible=false`; a correct retrospective time split does not confer certified real-time source availability, eliminate hidden source revisions or independently verify actual market spreads. EMA/proxy classification is only an illustrative label sign test. No broker executable entry/exit, spread, slippage, commissions, financing, Sharpe, predictive economic advantage, alpha or user ROI is claimed.
- **Single family per original source per SQLite registry** is a scientific anti-retesting gate, not a global federated ledger. The code does not magically prevent an operator from creating another registry or editing raw source outside AIDY, which is why later deployment must centralize permissions and storage.
- The original research blueprint recommends walk-forward, purge/embargo and full trial lineage, but its illustrative day numbering must **not** override AIDY's agreed Day26 scope, or Day30 real PDF/CSV deliverable.
- The progress checker must only mark Day26 scoped technical PASS after actual GitHub workflow+negative regressions+BigQuery replay+source hashes+code merge and Notion evidence. B07 owner sign-off, Day27 regime and Day28 evidence score are separate.
